### R2-F1 - original P2, resolved in source by C24b (15 October)

Location: `ResourceSpawner.cpp`, new backfill loop in `eccb53e1` / `Fable-resources2/cpp/resource-backfill.patch`: `mapSize = resourceSpawn->getSpawnMapSize()` is recomputed per candidate and compared using `roll * zones >= mapSize * 1000`.

Counterexample: 12 active zones, two existing maps, maxPool 5; backfill A has hash bucket 200, B bucket 100. First startup: A loses (2400 >= 2000); B wins (1200 < 2000), increasing maps to three. Next startup: A now wins (2400 < 3000), B is already present. The fixed hash did not prevent restart-dependent allocation. `test_release_formats.py` reproduces this arithmetic as a regression fixture; it does not assert that a particular real spawn has those buckets. The condition is a supported two-zone configuration and valid bucket values.

### C24b combined review: `98ad1d1d` + `3a0b154f`

- **Fixed-point argument:** `ResourceSpawner.cpp:217-260` counts maps outside the entire configured target set once per spawn. Backfill only inserts target maps, so that numerator cannot change. For unchanged active/backfill sets, scale, resource entry and existing non-target maps, every loser keeps the same threshold; winners already exist; capacity can only decrease. The actual total is checked against the scaled maximum before every insertion. Existing natural target maps are excluded too. Target order may choose which winner gets the last slot, but cannot cause another insertion on the next load. This assumes target zones remain loaded and insertion succeeds; config changes, expiration, ordinary spawn replacement and unrelated map edits are outside the guarantee.
- **Rounding/caps:** `scaledPool` (`ResourceSpawner.cpp:107-115`) computes `(pool * activeZones + scale / 2) / scale` with integer division, then bounds positive results to `1..activeZones`. At scale 10: 8 becomes 10 on 12 zones and 16 on 20; 1-3 becomes 1-4 on 12. Exact halves round up. Nonpositive scale/pool or no active zones returns the input. Tests compare with exact rational arithmetic for 1-40 zones, five denominators and pools 1-342 (the staged tree's largest pool bound); no realistic arithmetic overflow found. Existing maps above a lowered cap are retained, with no further additions.
- **Live default:** the header initializes scale to zero; `loadConfigData` reads the key explicitly. Engine3's `Lua::getGlobalInt` returns zero for a missing/non-number global (with an informational log), so missing means stock sizes. The tracked sandbox resource script has ten stock zones and neither new key. **Dev's script explicitly enables `poolScaleZones = 10`; promoting that script enables scaling.** Empty `backfillZones` prevents backfill, independently of scaling; it does not disable scaling of new spawns. This is source inspection, not a live configuration audit.
- **Restrictions/native/JTL:** the backfill guard skips nonempty zone restrictions; new-spawn selection still returns only the restricted zone before random removal, even though scaled bounds are passed. Native resources follow that restriction path. JTL still passes its existing `isJTL()` flag to density generation; unrestricted JTL types follow the galaxy-wide policy. Existing density maps are skipped, and the patch does not change resource statistics or expiration. Runtime preservation is untested.
- **Load-time top-up:** the block before backfill (`ResourceSpawner.cpp:189-204`) is byte-for-byte identical to `98ad1d1d^`: it tests the stock minimum and passes stock minimum/maximum minus existing count. Scaling is applied only to new-spawn bounds and the backfill cap/probability; it does not randomly top up old spawns to the scaled minimum. At the captured dev HEAD, `ResourceSpawner.cpp` is identical to `3a0b154f`.
- **Nonblocking documentation caveat:** source/Lua comments saying backfill reproduces creation-time odds, or what a spawn created today would give, are too strong. This is the conservative migration policy in [the original proposal](R2-idempotence-proposal.md): historical target maps are excluded, bucket probability is quantized to 1/1000, and capacity/order can reduce it. It does not promise exactly 80% coverage per existing resource or independent 80% marginals at the cap. Claude should describe that limitation in the comments; no additional blocking source defect is established.
