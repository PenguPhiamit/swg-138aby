absent. Patches already present are skipped, so it is safe to re-run; nothing is written if any check fails. Dry run
against dev today: `new files: 4, line patches to apply: 8, refused: 0`. `luac5.3 -p` passes on all staged files and the
snippet (`tools/luac_staged.sh`), and runs again on every touched file after applying.

Lair choice (`MissionManagerImplementation.cpp:1893-1925`): a lair qualifies when `minDifficulty <= player level + 5`
and `maxDifficulty >= min(player level - 5, minLevelCeiling)`; with none in range it falls back to the first lair below
player level + 5, and with none at all the slot stays empty. Ranges staged (creature levels from `mobile/hoth`):
tauntaun lair 60-72, ice mynock lair 64-76, raider camp 70-80, wampa lair 85-100, `minLevelCeiling = 75` so players above
80 still get mynock and raider missions as well as wampas. Nothing on Hoth is below level 62, so players under about 55
see no destroy missions here, as on Dathomir. Hunting (scout) missions need no staging: they read the zone's spawn
groups. Artisan and entertainer terminals are not placed (owner question 2).

**C++ part: none.** The mission manager has no planet list; `bh_target_zones` and everything above are Lua.

## C1b: Quartermaster Vell's salvage chain (3 jobs: collect, kill, deliver)

`screenplays/tasks/hoth/scavenger_quartermaster.lua` uses `ThemeParkLogic` exactly like `tasks/tatooine/aaph_koden.lua`
(a mission giver, a mission list, the two conversation handlers). The giver, Quartermaster Vell, stands at (44, 0, -2010)
next to the terminals. Each job is talk, do, return; the chain is neutral (no `faction` field).

1. **Collect** (`retrieve`): salvage tech Ria Baxx went to the Lucky Despot engine spur for a power regulator. The player
   finds her 600-900 m out (`distance = 600`), two ice mynocks (`hoth_ice_mynock`) are picking at the wreck and aggro
   on approach, Baxx hands over `quest_item/power_regulator.iff` ("Salvaged Power Regulator"). Reward 1500 credits.
2. **Kill** (`assassinate`): raider captain Thane Korro (`hoth_raider_captain_korro`, a named level 80
   `hoth_scavenger_raider` on the Zab mercenary body) with two raiders. Reward 3000 credits and his loot.
3. **Deliver**: carry `quest_item/current_alternator.iff` ("Salvaged Current Alternator") to broker Doro Kett on the
   drifts. Reward 2000 credits.

Four creature templates in `mobile/quest/hoth/scavenger_quartermaster_npcs.lua` (one file so one include line wires
them): giver on `dressed_merchant_trainer_02`, Baxx on `dressed_brigade_technician_human_female_01`, Kett on
`dressed_criminal_smuggler_human_male_01`; the two talk-to targets copy `talia_reede.lua` (ATTACKABLE + INVULNERABLE +
CONVERSABLE, the framework clears pvp on spawn). Conversation templates are registered by two lines appended to
`mobile/conversations/themepark/logic/mission_giver_conv.lua` and `mission_target_conv.lua` (after the yith_seenath
lines). `strings.tsv` carries every key the handlers read (`npc_1..6_N`, `player_1..5_N`, `npc_work/reward/reset/
backtowork/noloc_N`, waypoint names and descriptions, `npc_breech` for the hostile jobs, `npc_smuggle`/`notit`/
`dontknowyou` for the targets, `npc_dropoff_3`, plus `cant_work`, `notyet`, `next`, `npc_failure_n`). All client
objects used are in the archives the test client loads (`checks.json` -> `client_objects`: stock `patch_01`/`patch_05`/
`data_other_00`).

If the owner wants one anyway: a client deed IFF (copy of a stock vehicle deed, renamed, plus its CRC entry) is asset

`hoth_at_st` paths, which I can stage once the client object exists.

**Tauntaun rides: not purely Lua, so not staged.** What pre-CU Core3 checks (`PetManagerImplementation.cpp:104-128`,
`PetMenuComponent.cpp:188`): the pet must be a creature pet whose template has a `rider` slot
(`hasSlotDescriptor("rider")`), its appearance must have a row in `datatables/mount/valid_scale_range.iff`, the
player needs `outdoors_creaturehandler_support_04` to train it, and `managers/pet_manager.lua` -> `mountSpeedData`
needs a row for the appearance (otherwise it rides at the default speed). Against the client our test session loads:
- `object/mobile/shared_tauntaun_hue.iff` (stock, `patch_01.tre`) derives from `object/mobile/skeleton/shared_tauntaun.iff`
  -> `object/mobile/shared_mobile.iff`; no `mount_rider.iff` anywhere in the chain (the dewback's base
  `object/mobile/shared_dewback.iff` names it). Dev's `objects.lua` mirror shows the same: `slotDescriptorFilename =
  "abstract/slot/descriptor/player.iff"`.
- MTG's pet control device `object/intangible/pet/shared_tauntaun_hue.iff` names no `mount_pcd.iff` (the dewback's does).
- `datatables/mount/valid_scale_range.iff` (stock `patch_11_02.tre`) already has a tauntaun row; `appearance/tauntaun_hue.sat`
  is stock. `mountSpeedData` has no tauntaun row (Lua, trivial).
- `hoth_tauntaun.lua` has `tamingChance = 0`, and no tauntaun pet deed drops anywhere (MTG's `tauntaun_deed` pet deed and
  dev's server template exist but nothing hands them out).

So a rideable tauntaun needs two client objects changed or added in a tre (creature template with `mount_rider`, PCD
with `mount_pcd`; the server reads the same IFFs, `TemplateManager.cpp:469`), then Lua: `mountSpeedData` row
`{"appearance/tauntaun_hue.sat", 7.5, 1.3, 180, 660}` (dewback numbers as a start), `tamingChance` or a deed drop for
the pet, and the CH requirement stays as Core3 has it. Asset step first; I can stage the Lua lines the day the client
objects exist.
